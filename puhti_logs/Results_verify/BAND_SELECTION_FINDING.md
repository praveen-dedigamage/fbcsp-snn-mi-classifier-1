# Root cause: Results_verify differs from Results/ because the band-selection method changed, not because anything regressed — 2026-07-08

## What was checked, in order

1. `Results_verify`'s FP32/LDA/SVM numbers differed from the paper's Table III
   (`Results/`). Initial hypothesis: the Tier-0 SVM grid search overfits its
   hyperparameter choice to a small validation split ("optimizer's curse").
2. Checked `fold_0/pipeline_params.json`'s `svm_best_c`/`svm_best_gamma` across
   Subjects 8 and 9's five folds. Subject 8 picked the *exact untuned default*
   (`C=1, gamma='scale'`) in 4/5 folds — yet still lost ~9pp vs. the original.
   That's impossible if the grid search fits on the same data as the original
   run: `SVC` fitting is deterministic given fixed `(C, gamma)` and identical
   `feat_tr`/`y_tr` (no randomness enters without `probability=True`). So the
   **input features themselves must differ** between the two runs — this
   wasn't an SVM-tuning artifact.
3. Diffed `git diff 9850704 a9ceddf -- fbcsp_snn/baseline.py` to rule out a
   bug in the SVM-fitting logic itself. Confirmed: both versions fit on
   `feat_tr`/`y_tr` only, no leakage, no bug.
4. Compared `euclidean_alignment` between the two runs — both `true`. Ruled out.
5. Dumped every recorded config scalar from both runs'
   `Subject_8/fold_0/pipeline_params.json` side by side. **Found it**: the
   `bands` field.
   - Original `Results/`: `[[8,12],[6,10],[10,14],[14,18],[16,20], ...]` (12
     bands total) — non-standard, subject/fold-specific frequencies. The
     signature of **adaptive per-fold band selection**.
   - `Results_verify`: `[[4,8],[8,14],[12,18],[16,24],[20,30],[26,40]]` (6
     bands) — the literal fixed six-band scheme from `CLAUDE.md`.
   - Also: `csp_dual_end`, `csp_ledoit_wolf`, `encoder_type`, `filter_type`,
     `loss_type`, `tau_vr`, `train_batch_size`, `n_timesteps` are present in
     `Results_verify`'s JSON but **entirely absent** (not just different
     values — missing keys) from the original — confirming the original was
     generated by a meaningfully older version of `pipeline.py`.

## Root cause

`git log --reverse -S"euclidean_alignment" -- fbcsp_snn/preprocessing.py` and
`git show a9ceddf~1:run_puhti_array.sh` confirmed: before this session's
commit `a9ceddf` ("feat: ablation flags, hardware-reliability sweep, tuned
baselines, Cho2017 script"), `run_puhti_array.sh` passed
`--adaptive-bands --n-adaptive-bands 12`. That commit:

- Deleted `fbcsp_snn/band_selection.py` (316 lines — Welch PSD per trial +
  Fisher discriminant ratio scoring + greedy band selection with overlap
  constraint).
- Swapped `run_puhti_array.sh`'s `--adaptive-bands --n-adaptive-bands 12` for
  a hardcoded `--freq-bands "[(4,8),(8,14),(12,18),(16,24),(20,30),(26,40)]"`.
- **The commit message never mentions either change** — it only describes the
  ablation flags, reliability sweep, baseline tuning, and "removed dead
  sliding-window CSP augmentation" (a genuinely separate, correctly-described
  cleanup). Adaptive band selection was not dead code; it was the pipeline's
  documented primary band-selection method (`CLAUDE.md`'s Project Structure,
  Key Algorithms, Commands, and Default Hyperparameters sections all still
  described it as current, right up until this session's cleanup pass fixed
  those docs).

## Resolution

Asked the user directly whether dropping adaptive band selection was
intentional or accidental, since it's consequential and hard to cheaply
reverse (would need re-running the whole verification cycle again either way).

**User confirmed 2026-07-08: intentional — keep the fixed six-band design.**

Actions taken as a result:
- `CLAUDE.md` updated: removed `band_selection.py` from Project Structure,
  removed the "Adaptive band selection" algorithm subsection, replaced the
  `--adaptive-bands` example command (that flag no longer exists in
  `config.py`) with the actual current default behaviour, fixed the Default
  Hyperparameters block, removed the "adaptive pipeline" reference in the
  baseline-target paragraph.
- `main.tex` updated with `\TODO{}` markers at every location that states a
  number sourced from the old adaptive-band `Results/`: abstract,
  Table~III (`tab:per_subject_bnci`) caption, `tab:multiclass_bnci` caption,
  `sec:bnci` results prose, Discussion's filter-bank subsection (which now
  explicitly documents this history — three pipeline generations: 3
  non-overlapping fixed bands → 12 adaptive bands → 6 fixed overlapping
  bands), and the Conclusion's headline number.
- Related-Work sentence at `main.tex:250` that claimed "adaptive band
  selection" as a contribution was corrected to the two things that actually
  are current contributions (dual-end CSP, adaptive-threshold encoding).
- `fbcsp_snn/pipeline.py`'s `summary.csv` fieldnames fixed to include
  `n_timesteps`/`svm_best_c`/`svm_best_gamma` (found while investigating this;
  unrelated bug, already present in JSON but silently dropped from CSV).
- `puhti_logs/Results_verify/ANALYSIS.md`'s original SVM-tuning-is-broken
  conclusion marked superseded (see banner at top of that file).

is not a "verification retrain" of the pipeline behind the paper's existing
numbers — it **is** the pipeline the paper should describe, being run for the
first time end-to-end.
